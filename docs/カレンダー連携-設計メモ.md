# カレンダー連携 設計メモ（v0.4 候補）

予定を読み取り、びくたんとの会話に使う構想。

> **2026-07-29: 見送り。** 試作したところ、macOS の権限（TCC）の壁が想定より厚く、
> いまの配布形態（自己署名）では成立するか確かめられなかった。以下は調査の記録で、
> 再挑戦する時に同じところでつまずかないために残す。

## 何をしたいか

- 「このあと打ち合わせですね」のように、予定を踏まえて話す
- 予定の前に短く知らせる
- 「今日は空いていますね」のような、予定の無さも会話に使う

**やらないこと**: 予定の作成・編集・削除。読み取りだけにする。書き込みは事故が重く、びくたんの役割でもない。

## 方式の比較

### A. macOS のカレンダー（EventKit）を読む ← 推奨

macOS の「カレンダー」アプリに登録済みのアカウントから読む。Google カレンダーは、システム設定 →「インターネットアカウント」で追加されていれば対象になる。

- **認証**: 不要。macOS の許可ダイアログ（カレンダーへのアクセス）だけ
- **通信**: びくたん自身は外部と通信しない。同期は macOS がやる
- **対応範囲**: Google に限らず、iCloud も社内のExchangeも同じ経路で読める
- **前提**: 利用者が macOS カレンダーにアカウントを追加していること

この方式は、既存の `native/now-playing`（再生中の曲を読む）や `native/speech-recognizer.app`（音声認識）と**同じ作り**になる。実績のある形を増やすだけで済む。

### B. Google Calendar API を直接叩く（OAuth）

- **認証**: OAuth 2.0。利用者ごとに Google Cloud でクライアントを用意するか、配布物にクライアントIDを同梱する
- **問題**: 配布アプリにクライアントIDを含めるのは扱いが面倒（公開前提の設計にする必要がある）。利用者に Google Cloud の設定を求めるのは、マスコットアプリの導入としては重い
- **利点**: macOS の設定に依存しない。Google 以外は読めない

### C. 非公開の .ics URL を購読

- **認証**: 不要
- **問題**: Google の「限定公開URL」は、漏れると全予定が見える。設定に保存する対象としてリスクが高い
- **利点**: 実装が最小

## 推奨: A（EventKit）

理由は3つ。

1. **利用者に認証設定を求めない。** システム設定でアカウントを追加していれば、あとは許可ダイアログだけで済む
2. **びくたん自身が予定を外部へ送らない。** 読むのも同期も macOS の担当で、アプリは端末内で完結する
3. **既存の作りと揃う。** ネイティブヘルパーを1つ足すだけで、ビルド・同梱・権限の扱いは `speech-recognizer` の踏襲でいい

## 構成案

```
native/calendar-events.m     予定を読んでJSONで返す小さなコマンド
  ↓ 実行
main.js                      一定間隔で呼び、直近の予定を保持
  ↓
独り言・会話のプロンプトへ    「このあと14時に打ち合わせ」
```

`now-playing` と同じく、**引数なしで実行してJSONを1行返すだけ**の作りにする。常駐させない。

権限のために `.app` 形式が必要かは要確認（`speech-recognizer` はマイクとSpeechの権限のために `.app` にした）。`NSCalendarsUsageDescription` を Info.plist に書く必要がある。

## 保存するデータとプライバシー

**予定の本文を保存しない。** びくたんが持つのは、その時の会話に必要な最小限だけにする。

| 使うもの | 保存するか |
|---|---|
| 直近の予定のタイトル・開始時刻 | ✗ メモリのみ。終わったら捨てる |
| 「今日の予定の件数」 | ✗ 都度読む |
| カレンダー連携のオン/オフ | ✓ 設定として保存 |

会話AIへ送るかは**別の判断**になる。日記と同じく、送るなら明示する（「（外部のAIへ送ります）」）。予定は日記より機微なので、**既定はオフ**が妥当。

## 試作でわかったこと（2026-07-28）

`native/calendar-probe.m` を書いて、許可が取れるかを確かめた。**結論は「開発者のターミナルからは検証できない」。**

| 試したこと | 結果 |
|---|---|
| 素のコマンドとして実行 | `denied` |
| `.app` 形式（`NSCalendarsFullAccessUsageDescription` 付き）で実行 | `denied` |
| 要求の前後で許可状態を比較 | **`notDetermined` のまま変わらない** |

拒否されたのではなく、**許可ダイアログが出ていない**（利用者が拒否したなら `denied` に変わる）。

理由は TCC が**起動元のアプリ**に権限を紐づけるため。ターミナルやエディタから起動したコマンドは、その親アプリの権限コンテキストで動く。カレンダーを宣言していないアプリ経由では、子プロセスの要求は握り潰される。

`native/speech-recognizer.app` が動いているのは、**びくたん本体（`びくたん.app`）から起動されていて、本体の Info.plist が `NSMicrophoneUsageDescription` を宣言している**から。マイクとSpeechの宣言は Electron の既定テンプレートに元から入っており、これまで自分で足す必要がなかった。

**カレンダーは既定に入っていない。** 配布版の Info.plist を確認したところ、`NSCalendarsFullAccessUsageDescription` は無い。

### 決定的だったログ

`log show --predicate 'subsystem == "com.apple.TCC"'` に答えが出ていた。

```
Prompting policy for hardened runtime; service: kTCCServiceCalendar
requires entitlement com.apple.security.personal-information.calendars
but it is missing for responsible={identifier=com.anthropic.claude-code}
```

読み取れることが2つある。

1. **カレンダーは Info.plist の記述だけでは足りず、entitlement `com.apple.security.personal-information.calendars` が要る。** マイクは記述だけで通ったので、権限ごとに厳しさが違う
2. **TCC は親を辿って「責任アプリ」を決める。** 開発者のターミナルから起動している限り、責任アプリはそのターミナル側になり、そこに entitlement が無ければ弾かれる。**Finder からダブルクリックで起動**すれば、責任アプリはびくたん自身になる

### したがって、実装時に必要なこと

1. **びくたん本体の Info.plist にカレンダーの使用目的を足す。** `scripts/package-universal.mjs` に追記処理が要る（今は `NSCameraUsageDescription` を削る処理だけがある）
1. **本体とヘルパーの両方を、entitlement 付きで署名する。** `native/calendar-entitlements.plist` を `codesign --entitlements` へ渡す
2. ヘルパー側の `.app` にも同じ宣言を持たせる（`speech-recognizer` と同じ）
3. **検証は配布版のビルドでしかできない。** 開発時（`npm start`）は Electron の Info.plist を使うため、権限の宣言を制御できない

## 手元の環境について（2026-07-28 時点）

開発機には Google アカウントが連携済み。`~/Library/Accounts`（10項目）と `~/Library/Calendars`（6項目）に実体がある。

**ただし、これらは TCC で保護されていて、権限を持たないプロセスからは中身が読めない**（`ls` すら `Operation not permitted` になる）。この方式で実装する時は、**ヘルパーがカレンダーへのアクセス許可を得られるかどうかが最初の関門**になる。ファイルを直接読むのではなく、EventKit 越しに、許可を得た上で読む形にする。

利用者側にも「macOSのカレンダーにアカウントを追加していること」という前提が要るので、記事やREADMEにはその案内が必要になる。


## 見送りの判断（2026-07-29）

3回試して、いずれも許可ダイアログまで到達しなかった。壁は3つある。

| # | 壁 | 分かったこと |
|---|---|---|
| 1 | **entitlement が必須** | Info.plist の記述だけでは足りない。`com.apple.security.personal-information.calendars` が要る。マイクは記述だけで通るので、権限ごとに厳しさが違う |
| 2 | **責任アプリの判定** | TCC はプロセスの親を辿って「責任アプリ」を決める。開発者のターミナルから起動している限り、責任アプリはそちらになり、そこに entitlement が無ければ弾かれる。**開発者自身の環境では検証できない** |
| 3 | **データ隔離ができない** | 2を避けるには Finder から起動するしかないが、その場合 `BIKUNAVI_DATA_CHANNEL` が効かず、検証版が本番のデータフォルダを使ってしまう |

**未確認のまま残った点**: 自己署名（ad-hoc）で entitlement が有効になるのか。Apple Developer ID による署名が要るなら、**配布形態そのものを変える話**になる（現在は自己署名で配っている）。

### 再挑戦するなら

- まず「自己署名で entitlement が効くか」を、カレンダー以外の軽い権限で確かめる
- 検証は必ず**利用者自身が Finder から起動**する必要がある。開発者が `open` を実行しても責任アプリは変わらない
- 検証用のデータ隔離を、環境変数ではなく**アプリ内の仕組み**（起動引数やビルド時フラグ）で持つ
