# カレンダー連携 設計メモ（v0.4 候補）

予定を読み取り、びくたんとの会話に使う。まだ着手していない。この文書は方式を決めるためのもの。

## 何をしたいか

- 「このあと打ち合わせですね」のように、予定を踏まえて話す
- 予定の前に短く知らせる
- 「今日は空いていますね」のような、予定の無さも会話に使う

**やらないこと**: 予定の作成・編集・削除。読み取りだけにする。書き込みは事故が重く、びくたんの役割でもない。

## 方式の比較

### A. macOS のカレンダー（EventKit）を読む ← 推奨

macOS の「カレンダー」アプリに登録済みのアカウントから読む。Google カレンダーは、システム設定 →「インターネットアカウント」で追加されていれば対象になる。

- **認証**: 不要。macOS の許可ダイアログ（カレンダーへのアクセス）だけ
- **通信**: びくたん自身は外部と通信しない。同期は macOS がやる
- **対応範囲**: Google に限らず、iCloud も社内のExchangeも同じ経路で読める
- **前提**: 利用者が macOS カレンダーにアカウントを追加していること

この方式は、既存の `native/now-playing`（再生中の曲を読む）や `native/speech-recognizer.app`（音声認識）と**同じ作り**になる。実績のある形を増やすだけで済む。

### B. Google Calendar API を直接叩く（OAuth）

- **認証**: OAuth 2.0。利用者ごとに Google Cloud でクライアントを用意するか、配布物にクライアントIDを同梱する
- **問題**: 配布アプリにクライアントIDを含めるのは扱いが面倒（公開前提の設計にする必要がある）。利用者に Google Cloud の設定を求めるのは、マスコットアプリの導入としては重い
- **利点**: macOS の設定に依存しない。Google 以外は読めない

### C. 非公開の .ics URL を購読

- **認証**: 不要
- **問題**: Google の「限定公開URL」は、漏れると全予定が見える。設定に保存する対象としてリスクが高い
- **利点**: 実装が最小

## 推奨: A（EventKit）

理由は3つ。

1. **利用者に認証設定を求めない。** システム設定でアカウントを追加していれば、あとは許可ダイアログだけで済む
2. **びくたん自身が予定を外部へ送らない。** 読むのも同期も macOS の担当で、アプリは端末内で完結する
3. **既存の作りと揃う。** ネイティブヘルパーを1つ足すだけで、ビルド・同梱・権限の扱いは `speech-recognizer` の踏襲でいい

## 構成案

```
native/calendar-events.m     予定を読んでJSONで返す小さなコマンド
  ↓ 実行
main.js                      一定間隔で呼び、直近の予定を保持
  ↓
独り言・会話のプロンプトへ    「このあと14時に打ち合わせ」
```

`now-playing` と同じく、**引数なしで実行してJSONを1行返すだけ**の作りにする。常駐させない。

権限のために `.app` 形式が必要かは要確認（`speech-recognizer` はマイクとSpeechの権限のために `.app` にした）。`NSCalendarsUsageDescription` を Info.plist に書く必要がある。

## 保存するデータとプライバシー

**予定の本文を保存しない。** びくたんが持つのは、その時の会話に必要な最小限だけにする。

| 使うもの | 保存するか |
|---|---|
| 直近の予定のタイトル・開始時刻 | ✗ メモリのみ。終わったら捨てる |
| 「今日の予定の件数」 | ✗ 都度読む |
| カレンダー連携のオン/オフ | ✓ 設定として保存 |

会話AIへ送るかは**別の判断**になる。日記と同じく、送るなら明示する（「（外部のAIへ送ります）」）。予定は日記より機微なので、**既定はオフ**が妥当。

## 未確定・調べること

- [ ] `.app` 形式が必要か、素のコマンドで許可を取れるか（カレンダーは TCC の保護対象で、`speech-recognizer` をマイク権限のために `.app` にしたのと同じ事情が出る可能性が高い）
- [ ] 許可ダイアログを出すタイミング（起動時に出すと唐突。設定でオンにした時が自然）
- [ ] 予定を読む間隔（毎分は多い。5〜15分ごとか、予定の直前だけか）
- [ ] 終日予定・繰り返し予定の扱い
- [ ] 会話AIへ送る場合の既定（オフを推す）と、送る時の文面

## 手元の環境について（2026-07-28 時点）

開発機には Google アカウントが連携済み。`~/Library/Accounts`（10項目）と `~/Library/Calendars`（6項目）に実体がある。

**ただし、これらは TCC で保護されていて、権限を持たないプロセスからは中身が読めない**（`ls` すら `Operation not permitted` になる）。この方式で実装する時は、**ヘルパーがカレンダーへのアクセス許可を得られるかどうかが最初の関門**になる。ファイルを直接読むのではなく、EventKit 越しに、許可を得た上で読む形にする。

利用者側にも「macOSのカレンダーにアカウントを追加していること」という前提が要るので、記事やREADMEにはその案内が必要になる。
